COSTMOSYS

Cow Stress Monitoring System

Coursework · group project · public repositories · pilot stage · IoT · Machine Learning · Computer Vision · Firebase

Cow Stress Monitoring System. Two ESP32 boards read temperature and humidity in a cow barn, a relay switches the sprinkler valve and water pump, and a web dashboard shows the data. Separately, a YOLO26n model detects standing cows, lying cows and people in CCTV frames.

Read the case study

Problem

The barn needs temperature and humidity monitoring and automatic sprinkler control. Once configured, the right ESP32 can run the sprinkler logic without an internet connection.

Personal contribution

Group project. I trained the YOLO26n model, designed the schematic and wiring, built the ESP32 monitoring system, and developed the web dashboard, with Firebase handling telemetry and hosting. I used AI coding tools for parts of the implementation and reviewed every change.

Key decisions

  • Every sensor channel carries validity and sample age. Stale data is never shown as current, and an offline relay is not shown as OFF.
  • DS18B20 conversion is non-blocking. HTTP/TLS runs in its own task and passes snapshots through a queue.
  • Auto control uses mean temperature or aggregate THI. A threshold only starts a cycle, a started cycle runs its full duration, and cooldown counts from the real stop.
  • maxCyclesPerDay is one global quota. With no valid NTP time there is no new automatic cycle, and a reboot or clock rollback does not reset the quota.
  • Roles are enforced in Firebase Database Rules at field level. Account creation uses a second Auth instance so the admin session is not replaced.

Results

Two ESP32 boards share six DS18B20 and four DHT22 sensors. The model was fine-tuned from COCO yolo26n.pt for 40 epochs at 640 px, CPU only, in about 1 h 31 min.

The data came from 55 CCTV recordings (about 25.5 h). From 3,742 candidate frames, filtering by lighting, contrast, sharpness and time spacing left 999 images; 599 went to training. The firmware and dashboard have unit tests, and the Database Rules are tested on the Firebase emulator against a separate demo project, not production data.

Known limitations

  • It is still a pilot. Physical-device tests, sensor accuracy, radio range and installation safety need on-site checks.
  • Labels are automatic (Roboflow) and not fully human-verified, so the scores measure agreement with those labels at one location and one camera type, not operational accuracy.
  • Firmware TLS uses setInsecure(), device auth uses a legacy Database Secret, ESP-NOW is not encrypted, and settings do not persist after a reboot.
  • The CCTV path runs on a computer and is not connected to Firebase or the dashboard.

Stack

ESP32 (Arduino-ESP32 2.0.17), DS18B20, DHT22, SSR, ESP-NOW, Firebase Realtime Database and Auth, plain HTML/CSS/JS, YOLO26n, Ultralytics, PyTorch, OpenCV, Roboflow.

Multi-agent automation platform

Solo personal project · private backend repositories · Link: control UI demo (synthetic data) · AI · Software · Automation

Nine Node.js services run on one Ubuntu VPS (2 vCPU, 2 GB RAM) under systemd, plus a 9Router model gateway. The services are written in TypeScript. A master tracker watches the other agents, reviews their work, and handles alerts. Telegram and a React web dashboard handle commands and history.

I designed the system, set up the VPS, and built the dashboard. I review changes and approve deployments.

Read the case study

Goal

Keep nine automation agents running on one 2 GB VPS without checking each one by hand, with clear limits and recovery when something fails.

Personal contribution

Solo project. I designed the system, set up the VPS, and built the dashboard. I use AI coding agents for parts of the implementation and review every change before deployment. An orchestrator assigns work to specialised agents and checks exit codes, test totals, and logs. I approve changes before deployment.

What runs

  • Master tracker: checks every service every 60 seconds, detects bugs, applies guarded fixes, and schedules memory for heavy jobs.
  • Worker: runs coding jobs on separate copies of the code, with model fallback through the 9Router gateway.
  • Researcher: four scans per day (00:00, 06:00, 12:00, 18:00 WIB). Each scan sends 10 Spot, 10 Futures, and 10 DEX candidates with technical, fundamental, and news reasons.
  • Trading (spot and futures): reviews researcher candidates and decides entry, price trigger, or skip. Hard limits: max 3 entries per day, each at most 1/3 of daily starting capital, real trades only.
  • DEX: on-chain trading on Base following smart-money wallets, with the same daily entry limit and safety checks.
  • Campaign content (ContentRewards and TryBuzzer): video clip pipeline with local quality gates. The tracker audits every video before upload.
  • Affiliate content (Shopee): product video pipeline. The tracker audits every video before upload.
  • InternshipAgent: scrapes public job boards, filters by field, Jabodetabek location and period, removes duplicates, and sends a Telegram digest without LLMs.
  • LyNx Agent Control: React, TypeScript, and Express web dashboard with session and CSRF auth, service controls, and history views.

Key decisions

  • Services are written in TypeScript and run as plain JavaScript on the server, which keeps memory use low on a 2 GB machine.
  • A deploy never restarts a service during a trading scan or a content slot. Each deploy is backed up, checked for 10 minutes, and rolled back automatically if it fails.
  • Hard money rules: at most 3 entries per day, each at most 1/3 of the day's starting capital, real trades only. Changes to risk logic must pass tests that show trading decisions stay the same.
  • Memory is managed centrally. Before a video render, the tracker checks free RAM and pauses lower-priority agents if needed. It also detects jobs that stop making progress.
  • Agents Group: agents discuss failed or skipped work in Telegram and the dashboard. The tracker acts as judge and records lessons per agent. Lessons can only make agents more cautious.
  • Every video is audited by the tracker before upload. Telegram and the private web dashboard are control and audit channels; the public demo uses synthetic data.

Customer churn prediction

Coursework · Semester 5, Machine Learning · group of 3 · public repository · Machine Learning · Data · Streamlit

Predicts which telecom customers are likely to cancel. The group compared three classifiers on the public IBM Telco Customer Churn data, kept logistic regression, calibrated its probabilities and chose the decision threshold on training data only. A Streamlit app serves it with a single-customer form and batch CSV upload.

Read the case study

Problem

The app estimates churn risk so a retention team can decide whom to contact. The public IBM Telco Customer Churn dataset has 7,043 rows and 21 columns. Dropping 11 rows with a blank TotalCharges left 7,032 rows, of which 26.6% churned. The stratified 80/20 split gives 5,625 training rows and 1,407 holdout rows.

Personal contribution

Group project (three people). I selected and trained the model, built the web app, and deployed it to Streamlit. The public repository is under my account.

Key decisions

  • The model takes 18 input features. TotalCharges is left out to keep the form short and because it correlates strongly with tenure (r = 0.827 on the training data).
  • Three candidates were tuned with 5-fold GridSearchCV on F1: logistic regression, random forest and decision tree. Logistic regression won on cross-validated F1.
  • Random forest scored 0.8217 F1 on its training data against 0.6260 in cross-validation, which reads as overfitting.
  • class_weight="balanced" pushes raw scores upward, so the probabilities are calibrated with a 5-fold sigmoid fitted on the training data only.
  • The threshold search ran from 0.10 to 0.60 in steps of 0.01 on out-of-fold training probabilities. It picked 0.32, and 0.60 is the boundary for high risk.
  • At startup the app checks the SHA-256 of the model and calibrator files, and it validates every input before predicting.

Moving to 0.32 raises recall from 56.4% to 73.5% and cuts missed churners from 163 to 99, at the price of 243 false alarms instead of 115. ROC AUC is 0.8324. Seven unit and UI tests cover the app.

Known limitations

  • One public dataset from a single point in time. Real churn rates and feature distributions can differ, so it would need recalibration or retraining.
  • The correlations are associations, not causes.
  • The retention advice in the app is a set of static rules, not an uplift model or an A/B result.

Stack

Python, pandas, scikit-learn 1.9.1, Streamlit, matplotlib, joblib, unittest with Streamlit AppTest.

netwatch-rs

Live packet monitor and rule-based anomaly detector TUI

Personal project · Rust · pcap · etherparse · ratatui · Network security

A terminal tool that captures packets from an interface or replays a .pcap file, parses Ethernet/IPv4/IPv6/TCP/UDP/ICMP and DNS queries, and raises alerts for port scans, SYN spikes and DNS bursts.

Read the case study

Problem

Coursework covered routing, switching and Packet Tracer troubleshooting, but not packet-level inspection. I wanted a small project that proves I can decode raw bytes safely and recognise simple attack patterns without relying on a heavyweight IDS.

Architecture

A capture thread reads live packets or a pcap file and pushes them into a bounded channel. A second thread parses each frame with etherparse, updates 60-second traffic statistics and runs the detector. The UI reads an Arc<AppState> snapshot at 10 FPS, so terminal rendering never blocks capture.

Detection rules & trade-offs

Three sliding-window rules cover more than 15 unique destination ports in 5 seconds, more than 50 unacknowledged SYN packets in 1 second, and more than 50 DNS queries in 10 seconds. ACK packets clear matching SYN state by 4-tuple. Rules are explainable and cheap, but they need tuning per network and cannot detect slow or encrypted patterns.

Performance benchmark

Local release-mode measurement (Windows x86_64, 2026-11-22): 19,600,541 packets/s over 100,000 synthetic Ethernet/IPv4/UDP frames.

The benchmark times only the parser over a synthetic Ethernet/IPv4/UDP frame in release mode; live capture throughput also depends on the interface and driver.

Known limitations

  • Header and metadata inspection only; no TLS decryption or deep payload analysis.
  • IP fragments are counted as traffic but not reassembled before L4 parsing.
  • Live Windows capture requires Npcap; offline pcap replay needs no driver or root privileges.

Stack

Rust 2021, pcap, etherparse, ratatui, crossterm, clap, serde, serde_json, Python localhost traffic simulator.

WishNotes

Coursework · Semester 3, Web Programming · group project · full-stack development · Web · Laravel · SQLite

A Laravel app for leaving notes on themed boards. On the Christmas tree board, visitors pick a spot, choose an ornament, and attach a message. The other layouts are a bulletin board and a mailbox.

Read the case study

Personal contribution

Group project. I worked on both the PHP/Laravel backend and the frontend. I built the Blade screens and connected the board interface to the backend.

Board creation

After signing in, users give a board a title and description, pick a layout, and choose a public or private setting. The dashboard lists the signed-in user’s boards and shows the message count for each.

Placing a note

On the tree, visitors click where the ornament should go, choose from five designs, and write a message. The name is optional. The app stores the ornament’s x/y coordinates with the note so it can redraw it in the same spot when the board is reopened.

SCAFI

Coursework · Semester 4, mobile/IoT course · group of 4 · IoT · Embedded · Firebase · Telegram

Smart Control Against Fire and Intruder. A theft and fire alarm: an ultrasonic sensor, a DHT22 and buzzers. It raises a fire alert at 40 °C or higher and an intruder alert when something comes within 15 cm, then sends the alert to Firebase and Telegram.

How it works

Personal contribution

Group project (four people). I drew and assembled the schematic, fitted the electronics into the enclosure, and built the web dashboard.

Signal path

  1. DHT22 and ultrasonic sensor
  2. ESP firmware
  3. Firebase Realtime Database
  4. Web dashboard

The firmware also sends Telegram alerts directly.

Key decisions

  • Fire alert at temperature of 40 °C or more: a buzzer beeps every 150 ms, driven without blocking the loop.
  • Intruder alert at 15 cm or less: a second buzzer stays on.
  • Readings go to Firebase every 2 s, and temperature and humidity history every 10 s.
  • Each alert is saved to Firebase with an NTP-synced WIB timestamp and also sent to Telegram. A routine report goes to Telegram every 5 minutes.

Results

The photos show the prototype enclosure and dashboard. No figures are available for detection accuracy or response time.

Stack

ESP board, DHT22, ultrasonic sensor (NewPing), buzzers, Firebase Realtime Database, Telegram Bot API, NTP.

DoorLink

Coursework · Semester 4, Wireless Technology · group of 4 · IoT · Embedded · Networking · FastAPI

A door lock for a boarding house, built on an ESP32, an RFID reader and a MikroTik router. The door opens with a registered RFID card, or from a web page that is reachable only when you are connected to the boarding-house Wi-Fi.

How it works

Problem

The prototype was designed for shared housing. Unlike a physical key, a registered card or web account can be tied to an access log.

Personal contribution

Group project (four people). I developed the FastAPI backend and web dashboard, configured the MikroTik router, designed the circuit schematic, and assembled the prototype.

Web route

  1. Connect to the boarding-house Wi-Fi
  2. MikroTik limits the web page to that network
  3. Backend checks the user
  4. ESP32 opens the door

Card route

  1. RC522 reads the card
  2. ESP32 checks it against registered cards
  3. Door opens

Proposed design

  • A local whitelist on the ESP32 keeps card access working without internet, with offline logs cached and synced later.
  • Residents get hotspot and door access, guests get hotspot only, and an admin can monitor.
  • A database logs every access. The planned budget was Rp 243,700.

Results

The prototype opens with a registered card or from a web page on the boarding-house Wi-Fi. No timing or reliability figures are available.

Screenshot versions

The dashboard screenshots come from a local run with sample data. The interface is in Indonesian.

Stack

ESP32, RC522 RFID reader, relay or servo, FastAPI, Uvicorn, SQLModel (SQLite), Jinja2, Bootstrap 5, MikroTik RouterOS API integration (MASTER hotspot, RADIUS CHR/User Manager).

VitaLoop

Coursework · Semester 4, Cloud Technology · group of 3 · IoT · Embedded · Cloud · Data

A wristband prototype that streams heart-rate and blood-oxygen (SpO2) readings from a MAX30102 sensor to ThingsBoard over MQTT. It was built for coursework, not medical use.

How it works

Personal contribution

Group project (three people). I assembled the wristband, connected it to ThingsBoard running on Ubuntu in an AWS EC2 instance, and processed and analysed the sensor data in RStudio.

Signal path

  1. MAX30102 and microcontroller
  2. MQTT telemetry
  3. ThingsBoard on EC2
  4. RStudio analysis

Hardware list from the pitch deck: ESP32-C3 SuperMini, MAX30102, TP4056 charger, 0.96-inch OLED, 1S Li-Po.

Key decisions

  • Heart rate is a 4-sample average and accepted only between 40 and 180 BPM.
  • SpO2 is computed over 200 samples, with a fixed value of 80 when no finger is detected.
  • Telemetry goes out every 2 s as JSON with bpm and spo2.
  • ThingsBoard sits behind an Nginx reverse proxy with a self-signed certificate.

Results

The telemetry topic was tested with mosquitto_pub. ThingsBoard ran on Ubuntu 22.04 on an EC2 t2.medium instance. No sensor accuracy figures are available.

Stack

MAX30102, ESP32-C3 SuperMini, OLED, TP4056, MQTT, AWS EC2, Ubuntu 22.04, ThingsBoard 4.3.1, PostgreSQL 16, Nginx, RStudio.
